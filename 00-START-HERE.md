## Обязательный порядок работы

1. Сначала открыть действующий домен и проверить затронутые страницы, контент и поведение. Зафиксировать дату, URL и текущий серверный релиз/Worker version.
2. Затем проверить GitHub: `git status -sb`, `git remote -v`, `git fetch origin`, `git log -1 origin/main`. Проверить последний успешный deploy и сравнить его с доменом. Наличие нового коммита само по себе не доказывает публикацию.
3. Если production новее, сначала сохранить и сравнить опубликованные исходники/контент админки, вернуть допустимые изменения в GitHub. Не перезаписывать сайт старой локальной копией. HTML-сборка не заменяет исходные компоненты, а БД не заменяется seed-файлами.
4. Подготовить чистую рабочую ветку от сверенной версии. Незакоммиченные изменения других задач сохранить отдельно; использовать точные пути при `git add`. Внести свою правку в исходники, выполнить профильные проверки и просмотреть diff.
5. Обновить GitHub через обычный процесс проекта (PR/review/checks). Если задача включает публикацию — выполнить предусмотренный deploy, дождаться результата и проверить живой домен. Перед переключением релиза иметь проверенный способ отката. Не использовать старый архив поверх production.
6. После успешной проверки обновить основную локальную копию на SSD до итогового GitHub commit (`git pull --ff-only` только в чистой main). Сверить SHA, сборку/контент и статус Git. Если main занят незавершённой работой — не сбрасывать её; использовать чистую копию.
7. Обновить этот файл при изменении адресов, доступа, архитектуры, workflow или источника контента. В отчёте разделять: что совпало, что отличается, что не удалось проверить. Не писать «всё одинаково» по одному HTTP 200.

Приоритет восстановления: **опубликованное состояние → GitHub → локальная копия**. После правки итоговые код и публичный контент должны соответствовать опубликованной версии. Секреты, заявки, пользовательские БД, кэш и сборочные файлы не должны становиться одинаковыми с Git: для них отдельный защищённый backup и правила проекта.

## Как устроен

Статический сайт, Python build.py и GitHub Pages.

Версии зависимостей из текущего GitHub package.json: См. package.json / requirements.txt / build.py.

`src/` — исходники; `public/` — публичные ресурсы; `scripts/`/`tools/` — обслуживание; `.github/workflows/` — автоматизация, если присутствует. `dist/`, `node_modules/`, `.astro/` и `.wrangler/` пересоздаются инструментами, вручную не правятся. Точную структуру смотрите в профильной документации ниже.
